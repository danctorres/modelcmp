name: modelcmp
description: "Before you start a subagent, an Orca agent or a harness run (opencode, pi, omp, codex, claude, gemini, copilot) for any work (a review, a fix, a parallel run), run `modelcmp pick` and give it the model this skill says, even when your subagent tool has a default. Also use when the user asks which model to use for a task, which is cheapest or best, or to compare models: it answers from the models the user has, with their prices, benchmarks and favorites."
---

`modelcmp` joins the models the user can call with their prices, benchmark scores and the user's own choices. If the command is not found, tell the user to install it (`brew install danctorres/tap/modelcmp`), choose no model and do not look for a copy.

## Choose

```sh
modelcmp pick
```

Only when the prompt is large (a whole repo, a long log), add `--min ctx=600`, for 600,000 tokens. When you know the task and tier already, add `--task <task> --tier <tier>` for that line alone. It prints each task with what it is for, and under it a line per tier (tiers with the same model share one): the command that runs the model, the model's context and the user's `note` if any. Tasks with the same lines are listed together, above the lines they share. The command starts the harness the user has that model on, which is often not the one you are running in. Take one line:

1. **Task.** One marked `the user's own task` when the work fits it, even if a built-in task fits too (the user's `debugging` over `coding` for a bug). Otherwise the task whose description fits. When several do, the one naming what makes the work hard (a screenshot: `vision`, a long unattended run: `agentic`). When none does (docs, summaries), `overall`.
2. **Tier.** `free`, on the tasks that have that line, only when the user asks for a free model. Otherwise `low` for routine work (a mechanical edit, a bug with a clear cause, boilerplate), `mid` for ordinary work (a feature), `high` for the hardest (a subtle bug, a design, a long run where a mistake is costly).
3. **Check.** A `note` saying the model is bad at this kind of work rules it out: run again with `--not <id>`, the model's id in the line. Any other note changes nothing. `no model` on a tier: take the next tier up that has one, and with none, another task.
4. **Run** the command in your shell as printed, with the subtask in place of `"<prompt>"`, written for a model that knows nothing of your conversation and quoted for the shell (single quotes when it has `$`, a backtick or `"`). Name a file (an image, a log) by its path in it, never paste it. The command runs the prompt on that model and exits, printing the model's answer alone, or the end of the harness's log when it fails. It lets the harness edit files and run commands in the folder you run it in, so run it where the work is. Your own subagent tool takes your harness's models alone, so never pass it another harness's id, and never swap the model for one of yours because it is easier to start. Only for a model your harness has too, use your subagent tool instead: in Claude Code, a line with a Claude model (`modelcmp quiet claude --model claude-sonnet-5-5 ...` or `modelcmp quiet opencode run --model anthropic/claude-sonnet-5-5 ...`) is a subagent of that family (`sonnet`, likewise `opus` and `haiku`).
5. **Verify** the work before you use it (run the tests, read the diff, see that it changed what you asked and no test to make it pass): a model that failed still answers that it is done. When the work needs a review by another model, take a line from `reasoning` (or the user's own review task), on the tier you took for the work, with a different model than the one that did the work: `modelcmp pick --task reasoning --tier <tier> --not <id>`, the model in the line you took for the work, or your own when you did the work yourself. Tell it the subtask, to review the uncommitted changes without editing, and to end with PASS, or FAIL and the blocking issues with file:line. A line that runs `ollama run` or `llama-cli` cannot read files, so for it alone put the changes in the prompt: `'<prompt>'"$(echo; git diff HEAD; git diff --no-index /dev/null <new file>)"`, one `--no-index` per file the work added. Changes over 100 KB are too long for one shell argument, and a reply with neither PASS nor FAIL is no review: for either, take the next tier up for the review, and on `high`, review the changes yourself and tell the user. On FAIL, run the work's line again with the subtask and the issues, since that model knows nothing of its last run, or fix them yourself when you did the work, and review again. A third FAIL is that model failing the task: step up (6).
6. **Step up** to the next tier with another model only after the model fails the task. When `high` fails, tell the user. A run that fails on the account (no credit, a bad key, no login) is no model failing: do the work on a model of your own harness, and tell the user which account failed.

To start the subtask as an Orca agent (`orca worktree create --agent`, `orca agent launch` or `orca orchestration worker-start`), pass the line's harness as `--agent` and its model as `--model` in place of running its command. Orca's guide leaves `--model` out unless the user names one, and this skill is the user naming it. Orca sets the model of claude, codex and omp alone. For a line on another harness, start the harness yourself in an Orca terminal, `orca terminal create --worktree <worktree> --command '<harness> --model <id>'` (`pi --approve --model <id>` for pi), then `orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 60000`, and give it the subtask with `orca orchestration worker-start --terminal <handle> --worktree <worktree> --spec '<subtask>'`, or `orca terminal send --terminal <handle> --text '<subtask>' --enter` for a handoff. Orca keeps a terminal you made after `worker-release`, so close it with `orca terminal close --terminal <handle>`. Verify the agent's work as in step 5.

A model on the user's machine (ollama, llama.cpp) comes up as their favorite, or on a tier it scores higher on than the tier's pick. When the user asks for one, `modelcmp list --via ollama --via llama-cli` lists them. Make the one they name (or ask which) their favorite for the task with `modelcmp fav <task> <model> --tier <tier>`, once per tier it should take, then run `modelcmp pick --task <task>` and take its line as above. A line in pi, opencode or omp runs it as an agent that edits files and runs commands. One that runs `ollama run` or `llama-cli` is a model none of those has, which answers with text alone, so give it only work that needs no tools and tell the user that adding the model to an agent harness they have (pi's `~/.pi/agent/models.json`, opencode's or omp's config) under the provider `ollama` (`llama-cli` for llama.cpp) runs it as an agent, as another provider name leaves modelcmp unable to tell it is that model.

Only when you cannot run another harness (no shell, or the user says to stay in yours), `modelcmp pick --via <harness>` with yours (opencode, pi, omp, claude, codex, gemini, copilot): each line then has the id that harness takes in place of the command (in Claude Code, pass its family). A line ending in `(★ favorite ... run it with: <command>)` has the user's favorite on another harness: tell the user about it.

## Explain or compare

```sh
modelcmp compare <a> <b>            # side by side, opening with a verdict
modelcmp show <model>               # every benchmark, and its price where the user has it
modelcmp list --sort coding -n 10   # the best at coding first
```

Name a model by an id `pick` prints or part of its name (`sonnet-5.5`). Read these as text, `--json` is several times the size. `Price` is one blended $ per 1M tokens, and `-` is unknown, not free. Compare scores only within one task. `modelcmp <command> -h` has its flags.
